# Build on Auki P2P

`AukiPeer` is the application-facing runtime for authenticated Auki
peer-to-peer communication. It owns identity, Domain authority, transport,
optional relay reachability, mounted protocols, and ordered shutdown.

## The four pieces

~~~text
credentials + Domain + identity
              |
              v
          AukiPeer
      /       |        \
 authority  reachability  mounted protocols
              ^
              |
       discovery candidates
~~~

These pieces are related, but they solve different problems:

- **Authority** proves that one Peer ID currently belongs to the selected
  Domain.
- **Reachability** provides a route another peer can dial. A peer may use a
  relay, publish a direct route, or remain outbound-only.
- **Discovery** returns short-lived Peer ID, route, and protocol hints. It does
  not authenticate or authorize the peer.
- **Protocols** define the bounded conversation an application can call or
  serve. A peer serves nothing until an endpoint is mounted.

A **Domain** is the DDS authority and physical-space boundary. It is not a peer
manager or runtime object. `AukiPeer` is the runtime for one identity in one
Domain.

Every remote route is an untrusted hint. An exact protocol operation verifies
the expected Peer ID and Domain before exposing application data. Product
permission remains a separate decision: sharing a Domain does not automatically
grant camera access or permission to control a robot.

## Start a peer

The normal User or trusted App flow is:

1. authenticate;
2. list and select an accessible Domain;
3. load or create an identity;
4. authorize that Peer ID for the Domain; and
5. start `AukiPeer`.

`AukiPeerBootstrap` performs that sequence for native Rust applications.
Python, Web, and Swift expose the same lifecycle through thin bindings. Robot
and Compute products whose infrastructure already renews machine authority use
`AukiPeer::start_external` and keep their product-specific heartbeat, task, and
safety policy outside the SDK.

Identity ownership is explicit:

| Runtime | Authentication | Identity |
| --- | --- | --- |
| Native Rust | User or trusted App | normally persisted; one live owner |
| Python | User or trusted App | normally persisted; one live owner |
| Web/Wasm | User | ephemeral in the current facade |
| Swift/iOS | User | generated by the app; may be persisted by the app |

Never place an App secret in browser or mobile code. Never run two processes or
pods with the same persisted Peer ID.

## Opt in to protocols

`auki-protocols` has no default features. Enable only the wire contracts and
endpoints the application uses:

~~~toml
[dependencies]
auki-protocols = { path = "crates/auki-protocols", features = [
  "catalog-endpoint",
  "stream-endpoint",
] }
~~~

The public shape is consistent:

- a cloneable `Client` performs outbound operations;
- an `Endpoint` owns inbound registration and close; and
- a `Provider` supplies application data and admission decisions.

~~~rust,ignore
let endpoint = CatalogEndpoint::mount(peer.protocols(), provider)?;
let client = CatalogClient::new(peer.protocols());

let resources = client
    .fetch_resources_exact(remote_peer, route, ResourcesRequest::all())
    .await?;

endpoint.close().await?;
peer.shutdown().await?;
~~~

The SDK currently provides these families:

| Family | Active wire version | Rust | Web | Python | Swift |
| --- | --- | --- | --- | --- | --- |
| Info | v1 | call + serve | call + serve | call + serve | call + serve |
| Catalog | v3 resources, v4 maps | call + serve | call + serve | call + serve | call + serve |
| Registry | v3 | call + serve | call + serve | call + serve | call + serve |
| Blob | v1 | call + serve | call + serve | call + serve | call + serve |
| Message | v1 | send + receive | send + receive | send + receive | send + receive |
| Stream | v2 | consume + produce | consume + produce | consume + produce | consume + produce |

Catalog v2 remains wire-only because v3 embeds its locked log-row shape.
Endpoints do not silently negotiate older versions.

## Choose reachability and discovery separately

Relay allocation makes a peer reachable. Discovery lets other peers find its
route. Common combinations are:

| Application shape | Reachability | DDS discovery |
| --- | --- | --- |
| Browser controller that only calls peers | outbound-only | discover only |
| Robot, camera, or service accepting calls | relay-backed | discover and advertise |
| Private service reached through configuration | relay-backed or direct | disabled |
| Local native experiment | direct route | optional |

An outbound-only browser starts no relay booking and exposes no inbound route.
It can still discover and dial a remote peer's WSS route, but it cannot
advertise itself. Each relay slot yields one atomic TCP/WSS route pair so native
and browser callers can reach the same peer.

See [DDS discovery](discovery.md) for the API and trust boundary.

## Lifecycle rules

- Bound frames, queues, handler concurrency, and deadlines.
- Mount only the exact protocol versions the application serves.
- Treat discovered routes and `known_peers()` as observations, not authority.
- Close subscriptions, protocol endpoints, and application workers before the
  peer.
- Attempt cleanup even when the application operation fails.

Use [`auki-p2p`](../../crates/auki-p2p/README.md) directly only when building
transport or runtime machinery. Applications should normally stay on
`AukiPeer`.
