# Getting started with Auki P2P in Rust

This guide starts a real authenticated peer on the Auki dev environment. By
the end, it will have:

- a persistent Peer ID;
- authority for one selected DDS Domain;
- a direct TCP listener;
- an explicit Resource Catalog protocol handler; and
- clean, ordered shutdown.

You can then start a second peer and fetch its Resource Catalog over an
authenticated connection.

## Before you begin

You need:

- Rust `1.89.0` or newer;
- an Auki User account with access to a DDS Domain;
- that Domain's UUID; and
- two terminals if you want to test peer-to-peer communication.

App access-key/secret authentication follows the same flow and is shown near
the end. Never put an App secret in a browser or mobile application.

## Try the network without credentials

The SDK repository includes a self-contained loopback proof:

```sh
cargo build --locked -p auki-diagnostic-app
./examples/diagnostic-app/scripts/local-demo.sh
```

It starts two processes, exchanges catalogs in both directions, rejects
wrong-Peer and wrong-Domain credentials, and releases both listeners. Look for
the final `DEMO_OK`.

The credentials generated by this script are intentionally local and
short-lived. They are not usable outside the demo.

## 1. Create a Rust application

```sh
cargo new auki-peer-demo
cd auki-peer-demo
```

Until `v0.1.0` is tagged, pin every SDK crate to the same reviewed source
revision:

```toml
# Cargo.toml
[package]
name = "auki-peer-demo"
version = "0.1.0"
edition = "2024"
rust-version = "1.89"

[dependencies]
anyhow = "1"
auki-auth = { git = "https://github.com/aukilabs/auki-sdk", rev = "2ca8e6ed030e818faa40c380ca1dfc0d1447d25d" }
auki-domain = { git = "https://github.com/aukilabs/auki-sdk", rev = "2ca8e6ed030e818faa40c380ca1dfc0d1447d25d" }
auki-p2p = { git = "https://github.com/aukilabs/auki-sdk", rev = "2ca8e6ed030e818faa40c380ca1dfc0d1447d25d" }
auki-session = { git = "https://github.com/aukilabs/auki-sdk", rev = "2ca8e6ed030e818faa40c380ca1dfc0d1447d25d" }
tokio = { version = "1", features = ["macros", "rt-multi-thread", "signal"] }

```

Do not mix SDK revisions: identity, authority, Domain, and protocol contracts
are one coordinated release line.

## 2. Start one peer

Replace `src/main.rs` with:

```rust
use std::{env, fs, path::PathBuf};

use anyhow::{Context, Result, bail};
use auki_auth::{AuthClient, AuthEnvironment, Credentials, DomainSelection};
use auki_domain::{Domain, DomainConfig, Multiaddr, PeerId, ServedProtocols};
use auki_p2p::Identity;
use auki_session::Peer;
use uuid::Uuid;

#[tokio::main]
async fn main() -> Result<()> {
    let email = env::var("AUKI_EMAIL").context("AUKI_EMAIL is required")?;
    let password = env::var("AUKI_PASSWORD").context("AUKI_PASSWORD is required")?;
    let domain_id: Uuid = env::var("AUKI_DOMAIN_ID")
        .context("AUKI_DOMAIN_ID is required")?
        .parse()
        .context("AUKI_DOMAIN_ID must be a UUID")?;

    let state_dir = PathBuf::from(
        env::var("AUKI_STATE_DIR").unwrap_or_else(|_| "./state".to_owned()),
    );
    fs::create_dir_all(&state_dir)?;

    // Authenticate first. No P2P runtime exists yet.
    let auth = AuthClient::new(AuthEnvironment::dev())?;
    let auth_session = auth
        .authenticate(Credentials::user_password(email, password))
        .await?;

    // Domain selection is explicit and checked against current DDS policy.
    let selected = auth_session
        .accessible_domains()
        .await?
        .into_iter()
        .find(|choice| choice.domain.id == domain_id)
        .context("the authenticated User cannot access AUKI_DOMAIN_ID")?;

    // Reuse this file on every launch. Losing it changes the Peer ID.
    let identity = Identity::load_or_create(state_dir.join("peer.identity"))?;
    let prepared = auth_session
        .authorize_peer(DomainSelection::new(selected.domain.id), &identity.proof())
        .await?;

    let peer = Peer::new(prepared.peer_id.to_string(), "auki-peer-demo")
        .with_storage_root(state_dir);
    let recording = peer.start_session()?;

    let listen: Multiaddr = env::var("AUKI_LISTEN")
        .unwrap_or_else(|_| "/ip4/127.0.0.1/tcp/0".to_owned())
        .parse()
        .context("AUKI_LISTEN must be a multiaddr")?;
    let mut config = DomainConfig::new(prepared.domain.id, identity)
        .with_listen_addresses([listen])?;

    // A route is always stored under the Peer ID we expect to authenticate.
    let remote = match (
        env::var("AUKI_REMOTE_PEER_ID"),
        env::var("AUKI_REMOTE_ROUTE"),
    ) {
        (Ok(peer_id), Ok(route)) => {
            let peer_id: PeerId = peer_id.parse().context("invalid remote Peer ID")?;
            let route: Multiaddr = route.parse().context("invalid remote route")?;
            config = config.with_peer_routes(peer_id.clone(), [route])?;
            Some(peer_id)
        }
        (Err(_), Err(_)) => None,
        _ => bail!("set both AUKI_REMOTE_PEER_ID and AUKI_REMOTE_ROUTE, or neither"),
    };

    // Serving is explicit. Client methods remain available independently.
    let served = ServedProtocols::none().with_resources_v2();

    let domain = Domain::builder(&peer, &recording, config)
        .authority(
            prepared.verification_keys.clone(),
            prepared.initial_credential.clone(),
        )
        .served_protocols(served)
        .join()
        .await?;

    println!("READY");
    println!("  domain: {}", domain.domain_id());
    println!("  peer:   {}", domain.peer_id());
    for address in domain.listen_addresses() {
        println!("  listen: {address}");
    }

    if let Some(remote_peer) = remote {
        let catalog = domain.fetch_resources_catalog(remote_peer).await?;
        println!("remote resources: {}", catalog.resources.len());
    }

    println!("Press Ctrl-C to leave cleanly.");
    tokio::signal::ctrl_c().await?;
    domain.leave().await?;
    println!("LEFT");
    Ok(())
}
```

This program opts into serving Resource Catalog v0.2. Its catalog is empty
until the application registers logs or other resources; an empty authenticated
response is still a successful network proof.

## 3. Configure the first process

Use a secret manager for real applications. For a short local dev test:

```sh
export AUKI_EMAIL='you@example.com'
export AUKI_PASSWORD='...'
export AUKI_DOMAIN_ID='00000000-0000-0000-0000-000000000000'
export AUKI_STATE_DIR='./state-a'
export AUKI_LISTEN='/ip4/127.0.0.1/tcp/41001'
cargo run
```

Replace the Domain UUID with one returned for your account. Keep this process
running and copy its printed Peer ID.

## 4. Connect a second process

In another terminal, use a different state directory and listener. Reusing the
same User account is fine for a local experiment; the separate identity file
creates a distinct Peer ID.

```sh
export AUKI_EMAIL='you@example.com'
export AUKI_PASSWORD='...'
export AUKI_DOMAIN_ID='00000000-0000-0000-0000-000000000000'
export AUKI_STATE_DIR='./state-b'
export AUKI_LISTEN='/ip4/127.0.0.1/tcp/41002'
export AUKI_REMOTE_PEER_ID='<PEER_ID_PRINTED_BY_PROCESS_A>'
export AUKI_REMOTE_ROUTE='/ip4/127.0.0.1/tcp/41001'
cargo run
```

The second process should print:

```text
READY
remote resources: 0
```

The catalog request reaches application code only after both sides prove the
same Domain and their exact Peer IDs.

## Use App credentials instead

Trusted native and headless applications can replace the authentication call:

```rust
let auth_session = auth
    .authenticate(Credentials::app(app_access_key, app_secret))
    .await?;
```

Everything after authentication is identical. App secrets must not ship in a
browser, mobile app, public repository, image, or log.

## Keep a long-running peer alive

DDS credentials are intentionally short-lived. Schedule renewal using
`prepared.renew_at`, then install the returned keys before the credential:

```rust
let renewed = prepared.renewal.renew().await?;
let authority = domain.authority();
authority
    .install_verification_keys(renewed.verification_keys)
    .await?;
authority.install_credential(renewed.credential).await?;
```

After a successful refresh, schedule the next one from `renewed.renew_at`.

Retry transient failures within a bounded budget before literal credential
expiry. If renewal cannot complete, stop or fence the peer rather than silently
continuing without authority. The current low-level API deliberately leaves
scheduling to the host; the planned Rust peer facade will own this loop.

## Routes, relays, and discovery

This walkthrough uses an explicit direct route. Today:

- the SDK does not automatically discover peers;
- User/App relay allocation is not yet part of the public facade;
- a host may install direct routes or complete confirmed relay-circuit routes;
- `known_peers()` reports authenticated live connections and is not a route
  source.

`Domain::join()` can therefore return `Ready` with no routes while the peer is
still unable to contact anyone. Readiness means the local authenticated runtime
started successfully—not that a remote peer was discovered.

These concerns do not weaken authentication: every connection must still match
the selected Domain, signed credential, expected Peer ID, and secure transport
identity.

## Common failures

- **The identity and credential do not match:** reuse the identity file that
  was used for the Peer-ID proof; never replace it as an error fallback.
- **The Domain is ready but no peer is reachable:** install a direct or complete
  relay route under the expected remote Peer ID.
- **The remote rejects a request:** confirm that it explicitly serves that
  protocol version.
- **New connections stop working later:** renew the short-lived authority
  before its literal expiry.
