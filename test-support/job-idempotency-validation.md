# Keyed job submission validation

Offline validation for [#387](https://github.com/aukilabs/auki-sdk/issues/387),
2026-09-17. The SDK implements the caller contract of
[DMS #43](https://github.com/aukilabs/domain-manager-service/pull/43), which requires
[NCS #208](https://github.com/aukilabs/network-credit-service/pull/208).

These SDK checks use loopback HTTP fixtures or injected transports/clients. They
do not establish deployed support or repeat the backend PRs' PostgreSQL/credit
recovery tests. Enable keys only after the [rollout gate](../docs/reference/jobs.md#recover-a-keyed-submission)
is verified for the intended environment. No shared services, live credits,
provisioning, merge or deployment were used for this validation.

## Behavior covered

- Existing unkeyed submission sends no operation header and keeps its API.
- Keyed submission preserves the exact key and serialized specification through
  one 401 grant renewal for User, trusted App and imported ZITADEL sessions.
- Invalid keys fail before authentication; pre-cancelled or closed clients send
  nothing. Cancellation/timeouts after sending remain uncertain without replay.
- An uncertain keyed request sends once; explicit same-key recovery returns the
  fixture's original job ID. Keys are never generated by the SDK or bindings.
- Keyed 409 plus a valid numeric retry hint exposes `submission_in_progress` and
  its delay. Unkeyed, missing, malformed and overflowing hints remain conflicts.
  Error bodies and keys do not appear in diagnostics.
- Python and browser bindings preserve keys, retry metadata, cancellation and
  unkeyed behavior. Expo covers both its JavaScript/native bridge and actual Web
  adapter with an injected client; operation IDs remain separate from keys.
- Swift error mapping preserves the new kind/status/delay. Its generated native
  host exercises the typed keyed method, JSON shape and cancellation argument.
